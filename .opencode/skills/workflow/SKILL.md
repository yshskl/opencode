# Workflow Skill - 协作流程规范

## 目的

定义智能体协作的标准流程，确保各智能体之间的协作有章可循。

## 适用范围

task-coordinator 主智能体调度子智能体时使用本规范。

## 协作流程总览

```
用户输入
    │
    ▼
┌─────────────────────────────────────────┐
│           协作流程步骤                    │
├─────────────────────────────────────────┤
│ 1. 接收问题                              │
│ 2. 需求分析 (requirement-analyzer)       │
│ 3. 任务分解 (atomic-task skill)         │
│ 4. 质量预检 (quality-gates skill)        │
│ 5. 执行任务 (调度子智能体)                │
│ 6. 质量终检 (quality-gates skill)       │
│ 7. 结果汇总 (reporting skill)           │
└─────────────────────────────────────────┘
    │
    ▼
用户报告
```

## 各阶段详细说明

### 阶段1: 接收问题

**执行者**: task-coordinator

**输入**: 用户原始需求

**处理**:

- 理解用户需求的核心目标
- 识别项目类型（greenfield/brownfield/mixed）
- 初步判断需要哪些阶段的智能体

**输出**: 原始需求文本

---

### 阶段2: 需求分析

**执行者**: `requirement-analyzer` 子智能体

**输入**: 用户原始需求

**处理**:

- 收集和分析用户需求
- 生成结构化需求文档
- 识别功能需求和非功能需求

**输出文件**:

- `context/requirements.json` - 结构化需求
- `context/requirements.md` - 需求文档

---

### 阶段3: 任务分解

**执行者**: `atomic-task` skill

**输入**: 需求文档

**处理**:

- 将需求分解为可执行的原子任务
- 识别任务间的依赖关系
- 标记可并行执行的任务

**输出**: 原子任务列表

```json
{
  "tasks": [
    {
      "id": "task_1",
      "name": "设计数据库结构",
      "agent": "database-designer",
      "dependencies": [],
      "parallel": true
    },
    {
      "id": "task_2",
      "name": "实现用户API",
      "agent": "backend-developer",
      "dependencies": ["task_1"],
      "parallel": false
    },
    {
      "id": "task_3",
      "name": "实现用户界面",
      "agent": "frontend-developer",
      "dependencies": ["task_2"],
      "parallel": false
    }
  ]
}
```

---

### 阶段4: 质量预检

**执行者**: `quality-gates` skill

**输入**: 需求文档、原子任务列表

**处理**:

- 检查需求是否完整
- 检查任务分解是否合理
- 检查前置条件是否满足

**质量门禁规则**:

| 阶段     | 检查项       | 通过条件                    |
| -------- | ------------ | --------------------------- |
| 需求分析 | 需求完整性   | 至少3个用户故事             |
| 需求分析 | 需求一致性   | 无冲突需求                  |
| 需求分析 | 非功能需求   | 包含性能/安全/可用性至少2项 |
| 任务分解 | 任务可执行性 | 每个任务可独立执行          |
| 任务分解 | 依赖完整性   | 所有依赖关系已识别          |

**输出**: 检查结果（通过/不通过+建议）

---

### 阶段5: 执行任务

**执行者**: 调度子智能体

**输入**: 原子任务列表

**处理**:

1. **任务分发**
   - 根据任务类型选择合适的子智能体
   - 通过 context-manager skill 写入任务上下文到文件
   - 传递文件路径给子智能体

2. **执行模式**
   - **并行**: 依赖关系为空的可以并行执行
   - **串行**: 有依赖关系的按顺序执行

3. **上下文传递规则**

   ```
   传递给子智能体的信息：
   - 任务描述（简洁明确）
   - 上下文文件路径（任务相关文件）
   - 执行约束（限制条件）
   - 期望输出格式

   不直接传递完整代码/文件内容！
   ```

**输出**: 各任务的执行结果（写入上下文文件）

---

### 阶段6: 质量终检

**执行者**: `quality-gates` skill

**输入**: 各任务的执行结果

**处理**:

- 检查代码质量
- 检查测试覆盖率
- 检查文档完整性

**质量门禁规则**:

| 阶段     | 检查项     | 通过条件   |
| -------- | ---------- | ---------- |
| 开发完成 | 代码编译   | 无编译错误 |
| 开发完成 | 测试覆盖率 | > 80%      |
| 测试完成 | 测试通过率 | > 90%      |
| 审查完成 | 安全漏洞   | 无严重漏洞 |

**输出**: 检查结果（通过/不通过+建议）

---

### 阶段7: 结果汇总

**执行者**: `reporting` skill

**输入**: 所有任务的执行结果、质量检查结果

**处理**:

- 汇总各任务的执行情况
- 生成结构化报告
- 提供下一步建议

**输出**: 最终报告（返回给用户）

---

## 项目类型处理

### Greenfield（全新开发）

完整流程：需求分析 → 任务分解 → 架构设计 → 数据库设计 → 后端开发 → 前端开发 → 测试 → 审查 → 部署

### Brownfield（二次开发）

流程：逆向工程 → 需求分析 → 任务分解 → 架构设计 → 修改开发 → 测试 → 审查 → 部署

**逆向工程步骤**:

1. 调用 `explore` 分析现有代码
2. 调用 `requirement-analyzer` 从代码推导需求
3. 调用 `system-architect` 分析现有架构

### Mixed（混合模式）

流程：资产评估 → 需求分析 → 任务分解 → 选择性开发 → 测试 → 审查 → 部署

---

## 异常处理

### 任务失败

- 记录失败原因到上下文文件
- 继续执行其他独立任务
- 最终报告标记失败任务和原因

### 质量门禁不通过

- 记录不通过项和建议
- 可选择重试或标记为已知问题
- 继续后续流程

### 依赖缺失

- 检测到依赖任务失败时，标记后续任务为"阻塞"
- 不直接失败，等待人工决策
